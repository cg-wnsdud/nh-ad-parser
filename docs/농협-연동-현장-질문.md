# 농협 KL·ETLwithLLM 연동 현장 확인 질문

## 목적

이 문서는 구현안을 미리 확정하지 않고, 농협 방문 시 **호출 주체, 배포 위치, 입력과 출력
계약**을 먼저 합의하기 위한 질문지다. 기존 KL 비동기 광고 API 프로토타입은 미팅 자료로
유지하되, 답을 받은 뒤 운영용 KL API, ETL 클라이언트, `custom_extension`, 컨테이너
패키징 중 필요한 구현을 선택한다.

## 현재 확인된 사실

아래 내용은 전달받은 자료에서 직접 확인되는 범위다.

1. Knowledge Lake Custom Parser 예제에는 KL이 `POST /parsing`으로 파일을 보내고 작업
   UUID를 받은 뒤 `GET /parsing/result/{uuid}`로 상태와 결과 ZIP을 조회하는 비동기
   규격이 있다.
2. 해당 예제는 일반 문서를 Knowledge Lake/VectorDB에 적재하기 위한 HRC JSONL·JSON과
   이미지 ZIP 형식을 설명한다.
3. ETLwithLLM 가이드는 파일 분석 요청 API와 분석 상태·결과 조회 API를 별도로 설명한다.
4. ETLwithLLM 분석 요청의 프로젝트 설정 키는 가이드 p.29 기준
   `prj_config.extract_type`이며 값으로 `all`, `dla`, `parser`가 기재되어 있다.
5. 가이드 3장의 `custom_extension`에는 `extract()`, `transform()`, 사용자 정의 FastAPI
   router와 호스트 경로 마운트 예시가 있다.
6. 현재 `nh-ad-parser`는 회사 DGX-Spark의 PaddleX와 Gemma를 호출한다. 농협 폐쇄망에서는
   회사 모델 주소를 사용할 수 없다.
7. 이전에는 예제의 비동기 패턴을 적용해 광고용 `POST /ad/parsing`과
   `GET /parsing/result/{uuid}` 프로토타입을 구현하고 P1/P3 결과 ZIP을 보고했다.
8. 이 광고용 URL과 결과 형식이 농협 KL에 실제 등록 가능한지, ETLwithLLM과 어디서
   연결되는지는 아직 확인되지 않았다.

자료만으로 확인되지 않는 내용은 아래 질문에 답을 받아야 한다.

## 미팅 시작 시 전달할 현재 이해

> 저희는 앞서 제공받은 Custom Parser API 예제를 KL이 외부 파서 서비스를 비동기로
> 호출하는 규격으로 이해했습니다. 이를 기준으로 광고 파일을 `/ad/parsing`으로 접수하고
> UUID를 반환한 뒤, 같은 프로세스의 광고 파싱 함수를 실행하여
> `/parsing/result/{uuid}`에서 P1/P3 결과 ZIP을 반환하는 프로토타입을 구현했습니다.
> 당시에는 파싱 함수가 회사 DGX-Spark의 PaddleX와 Gemma를 호출했습니다.
>
> 이후 받은 ETLwithLLM 가이드를 보면 농협 OCR/DLA는 기존 PaddleX처럼 타일 이미지를
> 즉시 처리하는 API가 아니라 원본 파일을 분석 작업으로 요청하고 결과를 조회하는 구조로
> 보입니다. 그래서 기존 KL API가 계속 앞단이 되어 내부에서 ETLwithLLM을 호출해야 하는지,
> KL이 ETL 결과를 저희에게 넘기는지, 아니면 `custom_extension.transform()`에서 후처리를
> 실행해야 하는지 확인이 필요합니다. 저희가 기존 Custom Parser 예제를 이해하고 구현한
> 방향부터 맞는지 확인 부탁드립니다.

## 답변 후 구현 선택

| 확인 결과 | 구현할 항목 |
| --- | --- |
| KL이 별도 API를 호출 | 기존 KL 프로토타입을 농협 계약에 맞게 보완·운영화 |
| KL이 소스 패키지를 실행 | 농협 템플릿에 맞춘 `server/flow` 실행 패키지 |
| 우리 프로세스가 ETL 호출 | ETL 분석 요청·폴링·결과 조회 클라이언트 |
| ETL이 `transform()` 호출 | `custom_extension/implements` 후처리 어댑터 |
| 농협 DLA/OCR 결과 사용 | Default JSON → `AdDocument` 변환 및 좌표·표 검증 |
| 농협 vLLM이 현재 규격과 호환 | 주소·모델명 설정 분리 |
| vLLM 요청 형식이 다름 | VLM 클라이언트 어댑터 추가 |
| 최종 결과가 HRC | HRC JSONL/JSON/이미지 ZIP exporter 구현 |
| 최종 결과가 P1/P3 | 현재 review exporter 재사용 및 전달 규격만 연결 |

최소한 Q1~Q8과 Q13의 답이 정리되기 전에는 배포 구조나 API 서버를 확정하지 않는다.
