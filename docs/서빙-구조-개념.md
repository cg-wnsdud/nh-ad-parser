# 모델 서빙 구조 — 개념부터

작성일: 2026-09-08 · 대상: 이 프로젝트를 처음 보는 사람
확인 방법: `uv run python tools/probe_services.py` (구 저장소) · SSH `spark-fc87`

이 프로젝트는 **두 종류의 AI 모델**을 씁니다. 둘 다 우리 PC 가 아니라 사내 서버에서
돌고, 우리는 HTTP 로 부릅니다. 그 구조를 개념부터 정리합니다.

---

## 1. 용어 세 개

**모델(model)** — 학습이 끝난 결과물. 실체는 숫자가 잔뜩 든 파일(가중치)입니다.
그 자체로는 아무것도 못 하고, 프로그램이 메모리에 올려서 계산을 시켜야 합니다.

**추론(inference)** — 올려둔 모델에 입력을 넣고 답을 받는 것. 학습(training)의 반대말로
"이미 배운 것을 써먹는" 단계입니다. 우리가 하는 건 전부 추론입니다.

**서빙(serving)** — 모델을 **미리 GPU 메모리에 올려두고, 웹 서버처럼 요청을 받아
답해 주는 것**. 이게 왜 필요한지가 핵심입니다.

```
서빙 안 할 때                        서빙 할 때
──────────────────────              ──────────────────────
요청 올 때마다                        서버 켤 때 딱 한 번
  1. 모델 파일 읽기                     1. 모델 파일 읽기
  2. GPU 에 올리기   ← 수십 초~분        2. GPU 에 올리기
  3. 계산                              ↓ 그 뒤로는 계속 떠 있음
  4. 내리기                           요청 → 계산 → 응답  (수 초)
  다음 요청에 또 1번부터                요청 → 계산 → 응답
```

Gemma 서버 기동 로그를 보면 모델을 올리는 데만 **18.7초**, CUDA 그래프 준비까지
**2분 남짓** 걸립니다. 광고물 한 장 파싱에 VLM 을 40번 부르는데 매번 이걸 하면
쓸 수가 없습니다. 그래서 한 번 올려두고 계속 씁니다.

GPU 메모리가 한정돼 있다는 이유도 큽니다. 26B 모델 하나가 GPU 의 45% 를 점유합니다.
여러 사람이 각자 올리면 두세 명이면 꽉 찹니다. **한 번 올려서 여럿이 나눠 쓰는 것**이
서빙의 또 다른 목적입니다.

> 그래서 **서버 설정을 우리 마음대로 바꾸면 안 됩니다.** 다른 프로젝트가 같은 모델을
> 같이 부르고 있습니다.

## 2. dgx-spark 이 뭔가

`spark-fc87` 은 사내에 있는 **NVIDIA GPU 장비 한 대**입니다. 사람이 앉아서 쓰는
PC 가 아니라, 모델을 올려두고 여러 사람 요청을 받는 전용 기계입니다.

확인된 사양: NVIDIA Blackwell 세대 GPU, CUDA 13.0. 접속은 사내 WireGuard VPN 을
거쳐야 하고, 주소는 `10.90.0.103` 입니다.

이 한 대 위에 **도커 컨테이너 21개**가 떠 있습니다. 컨테이너는 "프로그램 하나를
필요한 환경째로 통째로 담아 격리해 돌리는 상자"라고 보면 됩니다. 우리가 쓰는 건
그중 3개뿐이고 나머지는 모니터링·검색·관리 도구입니다.

```
spark-fc87 (10.90.0.103)
│
├─ dgx-traefik          ← 문지기. 주소를 보고 어디로 보낼지 정함
├─ paddle-structurev3   ← OCR·레이아웃      ★ 우리가 씀
├─ litellm              ← LLM 교환대        ★ 우리가 씀
├─ vllm                 ← Gemma 실행 엔진    ★ 우리가 씀
│
├─ langfuse-* (5개)     ← LLM 호출 기록·분석
├─ dgx-prometheus / grafana / cadvisor / node-exporter / gpu-exporter  ← 감시
├─ open-webui / searxng-* / browserless / cg-elasticsearch  ← 다른 용도
└─ portainer_agent      ← 컨테이너 관리
```

## 3. 우리 요청이 어떻게 흘러가나

```
   우리 코드 (nh-ad-parser)
        │  HTTPS · WireGuard VPN 필요
        ▼
   pika.ihopper.co.kr          ← Traefik. 주소 앞부분만 보고 갈라 보냄
        │
        ├── /paddlex/  ──────►  paddle-structurev3      (OCR·레이아웃)
        │                       FastAPI · 포트 8081
        │
        └── /llm/      ──────►  litellm                 (교환대)
                                  │
                                  └──►  vllm  (127.0.0.1:8102)
                                          └── Gemma-4-26B
```

**Traefik** 은 아파트 경비실 같은 것입니다. `pika.ihopper.co.kr/paddlex/...` 로 오면
PaddleX 컨테이너로, `/llm/...` 로 오면 LiteLLM 으로 넘깁니다.

**LiteLLM 은 왜 한 겹 더 있나.** 모델 이름을 실제 백엔드에 연결해 주는 교환대입니다.
우리가 부르는 `spark-gemma-4-26b-NVFP4-MTP` 는 **LiteLLM 이 붙인 별명**이고, 실제
모델 이름은 `gemma-4-26b-NVFP4-MTP` 입니다. 같은 모델을 다른 장비(NHN Cloud B200)에
올린 것도 `b200-...` 라는 별명으로 등록돼 있어서, 이름만 바꾸면 백엔드가 바뀝니다.

> 2026-08-06 에 이 별명에 `spark-` 접두어가 붙으면서 VLM 호출이 전부 400 으로 죽은
> 적이 있습니다. 그런데 **OCR 은 멀쩡히 돌아서 산출물이 그럴듯하게 나왔습니다.**
> 모델 이름은 코드가 아니라 게이트웨이가 정한다는 걸 기억해야 합니다.

**vLLM 은 127.0.0.1 에만 묶여 있습니다.** 서버 자기 자신에서만 접근되므로 VPN 으로도
직접 못 갑니다. LiteLLM 이 유일한 문입니다.

## 4. OCR 쪽 — PP-StructureV3

담당자가 공유한 그림이 이 부분입니다. **그림의 값은 전부 정확합니다**(YAML 원본과
한 항목씩 대조 확인). 여기서는 그림이 다루지 않은 "그래서 이게 무슨 뜻인가"를 채웁니다.

### 파이프라인이란

PP-StructureV3 는 **모델 하나가 아니라 여러 모델을 순서대로 엮은 묶음**입니다.
설정 파일(`PP-StructureV3.yml`)이 "어느 자리에 어느 모델을 끼울지"를 적어 둔 것입니다.

```
이미지 한 장
   │
   ├─ ① 레이아웃 검출     PP-DocLayout_plus-L
   │     "여기는 제목, 여기는 표, 여기는 그림"  → 20종류로 분류
   │
   ├─ ② 영역 검출         PP-DocBlockLayout
   │     더 큰 단위로 페이지를 나눔 (2단 편집 같은 것)
   │
   ├─ ③ 글자 검출         PP-OCRv5_server_det
   │     "여기에 글자가 있다" → 네모 상자만 찾음. 내용은 모름
   │
   ├─ ④ 줄 방향 판별      PP-LCNet_x1_0_textline_ori
   │     세로쓰기·뒤집힌 글자 보정
   │
   ├─ ⑤ 글자 인식         korean_PP-OCRv5_mobile_rec
   │     상자를 오려서 "이 그림은 '금리'다" → 실제 글자로 변환
   │
   └─ ⑥ 표 인식           SLANeXt_wired / SLANet_plus + RT-DETR-L
         표의 행·열·셀 좌표를 찾음
```

**③ 검출과 ⑤ 인식이 나뉜 게 중요합니다.** 글자가 안 나올 때 "상자를 못 찾은 것"인지
"상자는 찾았는데 잘못 읽은 것"인지에 따라 손볼 곳이 완전히 다릅니다.

### 그림에서 특히 눈여겨볼 값

| 값 | 뜻 | 왜 중요한가 |
| --- | --- | --- |
| `korean_PP-OCRv5_mobile_rec` | 글자 인식이 **경량(mobile)** 모델 | 검출은 server 인데 인식만 mobile 이라 이상해 보이지만, **PP-OCRv5 에 한국어 server 인식 모델이 아예 없습니다.** 이게 한국어 정확도 천장(88.0%)입니다 |
| `limit_side_len 736 / min` | 짧은 변이 736 미만이면 확대 | 서버 기본값. **우리는 요청에서 2500/max 로 덮어씁니다** — §6 참고 |
| `threshold` 클래스별 | text 0.40, 제목 0.30, 표 0.50 … | 20개 클래스마다 다르게 조율돼 있음. 낮출수록 더 많이 잡고 헛검출도 늘어남 |
| `layout_merge_bboxes_mode` | 겹친 박스 처리 방식 | 그림의 주석이 정확합니다 — `union` 은 **좌표를 합치는 게 아니라 필터를 생략**하는 것 |
| `score_thresh = 0.0` | 인식 결과 신뢰도 하한 없음 | 자신 없는 글자도 전부 내보냄. 걸러내는 건 우리 몫 |
| 표 내부 `box_thresh 0.4` | 본문 0.6 보다 낮음 | 표 안 작은 글씨를 더 적극적으로 잡으려는 조율 |

### 그림 오른쪽 아래 "비활성 기능"의 의미

`PP-Chart2Table`(차트 → 표), `PP-FormulaNet_plus-L`(수식), 인장 인식, 문서 전처리는
**설정 파일에 이름은 있지만 스위치가 꺼져 있습니다.** 그림의 지적이 맞습니다 —
"YAML 에 적혀 있다 = 매번 실행된다"가 아닙니다.

여기에 하나 덧붙일 사실이 있습니다. **요청에 `useChartRecognition: true` 를 실어
보내면 HTTP 500 으로 죽습니다.** 서버가 차트 모듈 없이 파이프라인을 구성한 채로
떠 있어서, 가중치 파일은 있어도 요청만으로는 못 켭니다(실측 확인). 차트 인식을
쓰려면 서버 설정 변경 + 재기동이 필요합니다.

## 5. VLM 쪽 — Gemma (그림에 없는 부분)

OCR 이 "글자를 읽는" 모델이라면, VLM(Vision-Language Model)은 **이미지를 보고
말로 답하는** 모델입니다. 우리 파이프라인은 OCR 만으로 안 되는 판단에 씁니다 —
카드형 광고를 몇 장으로 나눌지, 흐린 글씨를 다시 읽을지 같은 것들입니다.

```
실제 모델        nvidia/Gemma-4-26B-A4B-NVFP4
우리가 부르는 이름  spark-gemma-4-26b-NVFP4-MTP     ← LiteLLM 별명
실행 엔진        vLLM
컨텍스트         131,072 토큰
양자화           NVFP4 (4비트)
KV 캐시          fp8 (8비트)
투기 디코딩       MTP, 초안 4토큰
구조화 출력       xgrammar
이미지 예산       max_soft_tokens = 1120
GPU 점유         45%
```

### 낯선 용어 풀이

**토큰** — 모델이 글자를 쪼개서 보는 단위. 한국어는 한 글자에 대략 1~2 토큰입니다.
**컨텍스트**는 한 번의 요청에 넣을 수 있는 총량이고, 지금은 131,072 입니다.

**양자화(quantization)** — 모델 가중치를 낮은 정밀도로 압축해 GPU 메모리를 줄이는 것.
`NVFP4` 는 4비트입니다. 가볍고 빠른 대신 미세하게 부정확할 수 있습니다.
**추론 전용 체크포인트라 이 상태로는 추가 학습(파인튜닝)이 안 됩니다.**

**KV 캐시** — 이미 읽은 토큰의 계산 결과를 저장해 두는 메모리. 여기서는 `fp8` 로
압축돼 있습니다.

**투기 디코딩(MTP)** — 작은 초안 모델이 다음 4토큰을 미리 찍고 본 모델이 검증하는
속도 향상 기법.

**구조화 출력(xgrammar)** — "JSON 으로 답해 줘"라는 부탁이 아니라, **정해진 형식에
안 맞는 글자는 아예 생성되지 못하게 막는 장치**입니다. 우리가 `response_format:
json_schema` 로 부르면 이 엔진이 강제합니다.

### 이미지는 크기와 무관하게 같은 값을 씁니다

`max_soft_tokens = 1120` 때문에 **이미지 한 장이 항상 약 1,100 토큰**으로 눌러
담깁니다. 실측:

| 보낸 이미지 | 소모 토큰 |
| --- | --- |
| 448 × 448 | 1105 |
| 896 × 896 | 1105 |
| 896 × 2400 | 1096 |
| 1400 × 4000 | 1080 |

크게 보낸다고 더 잘 보이지 않습니다. 세로로 긴 광고를 통째로 보내면 축소율만
커져 작은 글씨가 사라집니다. 그래서 코드가 캔버스를 가로 밴드로 잘라 여러 번
보냅니다.

## 6. 우리 요청이 서버 기본값을 덮어씁니다 — 그림에 없는 층

담당자 그림은 **설정 파일에 적힌 값**을 정리한 것이고, 그림 하단 주석대로 "요청 API 의
기본값과 실행 환경 설정은 섞지 않았"습니다. 실제로 돌 때는 한 겹이 더 있습니다.

PaddleX 의 `/layout-parsing` 은 **39개 파라미터**를 받고, 요청에 실어 보낸 값이
그 요청에 한해 설정 파일을 이깁니다. 우리는 8개를 보내고 31개는 서버 기본값에
맡기고 있습니다.

| 항목 | YAML(그림) | 우리가 보내는 값 | 왜 |
| --- | --- | --- | --- |
| `textDetLimitSideLen` / `Type` | **736 / min** | **2500 / max** | 축소로 fine-print 가 깨지는 것을 막으려고 |
| `layoutMergeBboxesMode` | **클래스별 딕셔너리** | **`"small"` 스칼라** | 사진형 카드 콜라주가 한 덩어리로 뭉치는 것을 막으려고 |
| `useTextlineOrientation` | **True** | **False** | 방향 분류기가 얇은 회색 글씨를 뒤집어 읽은 사례가 있어서 |
| `useDocOrientationClassify` / `Unwarping` | False | False | 동일 |
| `useFormulaRecognition` | False | False | 동일 |

**두 번째 줄이 특히 중요합니다.** 그림에 나온 클래스별 병합 설정(제목·이미지·수식·
차트만 `large`, 나머지 16종은 `union`)은 서버가 조율해 둔 것인데, 우리가 문자열
하나를 보내면 **20개 클래스 전부가 `small` 로 균일해집니다.** 카드 콜라주 문제를
막은 선택이라 지금은 유지하고 있지만, "기본값 large 를 small 로 바꿨다"가 아니라
"조율표를 통째로 지우고 있다"가 실제로 일어나는 일입니다.

반대로 `layoutThreshold` 는 안 보내므로 그림의 클래스별 값이 그대로 살아 있습니다.

> **이 덮어쓰기는 안전합니다.** 요청 파라미터는 그 요청에만 적용되고 다른 프로젝트에
> 영향이 없습니다. 서버 설정을 바꾸는 것과는 전혀 다릅니다.

## 7. 두 모델의 성격이 다릅니다

같은 서버에 있지만 신뢰도의 성격이 반대입니다. 이걸 모르면 결과를 잘못 읽습니다.

| | OCR (PaddleX) | VLM (Gemma) |
| --- | --- | --- |
| 같은 입력 → 같은 결과 | **예** (결정적) | **아니오** |
| 재실행하면 | 같은 값 | 달라질 수 있음 |
| 정본으로 쓰는가 | **예. 글자의 정본은 OCR** | 아니오. 후보·판단만 |

**VLM 이 흔들리는 이유**는 모델이 아니라 서버 설정에 있습니다. fp8 KV 캐시,
prefix caching, chunked prefill, 투기 디코딩 네 가지가 동시에 켜져 있어서, **다른
사람의 요청이 같이 처리되는 상황에 따라 계산 순서가 바뀝니다.** 확률이 간발의 차인
지점에서 답이 갈립니다. `temperature=0` 으로도 못 막고 클라이언트에서 손쓸 방법이
없습니다.

그래서 이 프로젝트의 원칙이 **"글자의 정본은 OCR, VLM 은 후보"** 입니다. VLM 판독은
`vlm_region_reading` 이라는 별도 칸에만 적히고 OCR 원문을 덮지 않습니다. 지금 기본
설정에서는 그 경로 자체가 꺼져 있습니다(`REGION_READING_MODE=off`).

그리고 **VLM 을 쓰는 단계는 1회 실행 결과로 판단하면 안 됩니다.** 실측으로 같은
코드 재실행에 골드 33블록 중 4개(12%p)가 움직인 적이 있습니다.

## 8. 직접 확인하는 방법

### 서버 접속 없이 (VPN 만 있으면)

```bash
uv run python tools/probe_services.py        # 구 저장소 nh-ad-review-poc
```

살아 있는지, 받는 파라미터 39종, **서버가 실제로 적용한 값**, Gemma 모델 목록과
컨텍스트 길이가 나옵니다. 서버 실제 적용값은 추론 응답의 `model_settings` /
`overall_ocr_res.text_det_params` 에 실려 오므로 아무 이미지나 한 장 보내면 읽힙니다.

curl -s 127.0.0.1:8102/v1/models

## 9. 요약

- **서빙**은 모델을 미리 GPU 에 올려두고 HTTP 로 답해 주는 것. 로딩 시간과 GPU 메모리
  때문에 필요하고, 그래서 **여럿이 공유**하므로 설정을 함부로 바꾸면 안 됩니다.
- **OCR(PaddleX)** 은 모델 여러 개를 엮은 파이프라인이고, 담당자 그림이 그 설정을
  정확히 정리한 것입니다. 한국어 인식은 mobile 모델뿐이라 88% 가 천장입니다.
- **VLM(Gemma)** 은 그림에 없는 다른 서버입니다. 4비트 양자화 추론 전용이라 파인튜닝은
  불가하고, 이미지는 크기와 무관하게 약 1,100 토큰으로 눌립니다.
- **요청마다 서버 기본값을 덮어쓸 수 있고** 우리는 실제로 3개를 덮어쓰고 있습니다.
  이건 그 요청에만 적용되므로 안전합니다.
- **OCR 은 결정적, VLM 은 비결정적.** 글자의 정본은 OCR 입니다.
