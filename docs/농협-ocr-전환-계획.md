# 농협 OCR 전환 계획 — PaddleX → ETL with LLM

규격 원문 정리는 [농협-ocr-연동-규격.md](농협-ocr-연동-규격.md).
이 문서는 **우리 코드와의 격차, 전환 설계, 되물을 것**을 다룬다.

---

## 1. 배경 — 무엇이 바뀌는가

지금 파이프라인은 사내 DGX-Spark 의 두 서비스를 부른다.

```text
nh-ad-parser
 ├─ HTTP → PaddleX PP-StructureV3   (PADDLEX_URL)  레이아웃 + OCR
 └─ HTTP → Gemma VLM                (GEMMA_URL)    Reader / Judge / 스윕
```

농협 요구는 이 중 **OCR 쪽을 농협 내부 플랫폼으로** 돌리라는 것이고, 그 플랫폼이
AgileSoDA `ETL with LLM` 이다. 확인해야 할 전제가 셋 있다.

1. **"OCR 교체" 가 아니라 "레이아웃+OCR 계층 교체" 다.** ETL 이 주는 것은 영역 종류·
   좌표·텍스트·표 HTML 이다. PP-StructureV3 가 하던 일 전체에 대응한다.
2. **VLM 은 이번 문서 범위 밖이다.** 광고심의는 VLM Reader/Judge 가 정확도의 핵심인데
   (`REGION_READING_MODE`, 저신뢰 재판독, 밴드 스윕), 농협 내부 VLM 을 쓸 수 있는지는
   이 문서에 없다. **OCR 만 바꾸면 VLM 은 여전히 DGX-Spark 를 향한다.**
3. **`kl_parser` 의 전제가 깨진다.** 기존 README 는 "농협 내부의 PaddleX OCR 과 VLM
   GPU 서비스를 HTTP 로 호출" 을 전제로 적혀 있다. 농협이 주는 것은 PaddleX 가 아니다.

### 두 통신 방향을 헷갈리지 말 것

| | 규정문서 트랙 (기존) | 광고물 OCR (이번) |
|---|---|---|
| 규격 | `1.awx_custom_parser_example_api` | `ETLwithLLM API가이드 v1.1.0` |
| 방향 | **농협 KL → 우리** (`POST /parsing`, `src_file`) | **우리 → 농협 ETL** (`POST /etl/auto/start`) |
| 우리 역할 | 서버 (Custom Parser 구현) | 클라이언트 |
| 산출물 | `_hrc.jsonl` / `_hrc.json` / `_img.zip` (zip) | ETL 이 만든 Default JSON 을 우리가 소비 |

기존 규격의 `parser_info.prop` 에 `supplier`/`url`/`key` 로 **OCR 제공자 정보를
넘겨주는 자리**가 있었다. 이번 ETL 이 그 자리에 들어오는 물건인지, 별개 경로인지는
확인이 필요하다(질문 Q3).

## 2. 요청한 6항목 대비 커버리지

메신저로 요청한 항목이 이 58쪽에서 어디까지 답변됐는가.

| 요청 항목 | 상태 | 내용 |
|---|---|---|
| OCR API 입력 형식·스키마 | **충족** | `POST /api/v1/etl/auto/start`, multipart `tr_data`+`upfiles`, `prj_config` 15개 옵션 전부 (규격 §3~4) |
| OCR API 출력 형식·스키마 | **충족** | Default JSON 계층형 정의 + 표/셀 구조 (규격 §6) |
| 실제/예시 Request·Response 샘플 | **충족** | curl·Python 샘플, 응답 캡처 다수 (규격 §3, §6, §7) |
| 이미지·PDF 등 파일 전달 방식 | **부분** | multipart `upfiles` 는 명확. **허용 확장자 목록이 없다.** 예시가 전부 PDF (질문 Q1) |
| 호출 파라미터 및 인증 방식 | **부분** | 파라미터는 완전. 인증은 쿠키 토큰 방식만 있고 **필수 여부·계정 발급 절차가 없다** (질문 Q2) |
| 오류 응답 형식·주요 Error Code | **부족** | 형식은 관측 가능하나 **코드 정의표가 없고**, 형식이 두 가지 섞여 있다 (규격 §9.3, 질문 Q6) |

문서 자체는 충실하다. 다만 **우리가 필요한 순간에 없는 것**이 세 가지 — 입력 확장자,
인증 필수 여부, 에러 코드 정의 — 이고 전부 회신으로 받아야 한다.

## 2-1. 무엇이 사라지고, 무엇이 그대로 남는가

전환의 크기를 오해하기 쉬운 자리다. **새로 만드는 코드는 변환기 하나뿐이고, 그 아래는
전부 그대로 재사용된다.**

```text
[지금]
파일 → triage(텍스트레이어 판정) → 200dpi 렌더 → 타일링
     → PaddleX 호출 → 좌표복원 · 중복제거
     → 영역조립 → 템플릿선택 · 구분라벨 → P1(evidence) / P3(review-input) → 다음 심의 단계

[ETL 전환 후]
파일 → ETL 업로드 → 폴링 → 결과 JSON            ← 플랫폼이 렌더 · 페이지분리 · OCR 을 내부에서 한다
     → 변환기 (JSON → LayoutBlock + Line)        ← ★ 새로 만드는 유일한 코드 (ocr/etlwithllm.py)
     → 영역조립 → 템플릿선택 · 구분라벨 → P1 / P3 → 다음 심의 단계   ← 손대지 않는다
```

| 계층 | 전환 후 | 근거 |
|---|---|---|
| `ingest/triage.py` (텍스트레이어 판정) | **자리 없음** — 플랫폼의 `ocr_only` 가 대응 | 가이드 p.29 "ocr만 사용 또는 ocr + pdf reader 병합" |
| `ingest/canvas.py` (200dpi 렌더) | **자리 없음** — 플랫폼이 내부 변환 | p.55 `width`/`height` = "이미지 변환 후" |
| `ocr/tiling.py` (타일 분할·복원·중복제거) | **자리 없음** — 페이지 단위로 결과가 온다 | p.30 `start_page`/`end_page` |
| `ocr/paddlex.py` | ETL 로 대체 (기준선으로 보존) | — |
| **변환기** | **신규** — `ocr/etlwithllm.py` | 작성 완료 |
| `layout/regions.py` 이하 전부 | **그대로** — 라벨 매핑 5줄만 추가 | 완료 |
| `review/` (템플릿·라벨링·P1/P3) | **그대로** | — |

즉 "다음 심의 단계로 넘기는 코드" 는 **새로 작성할 대상이 아니다.** 출력 계약(P1/P3)은
이미 [출력-계약.md](출력-계약.md) 에 정의돼 있고 OCR provider 가 바뀌어도 변하지 않는다.
바뀔 여지가 있는 곳은 G1(줄 신뢰도 없음 → `needs_review` 판정)과 G11(표 정본) 두 곳뿐이며,
둘 다 **현장 실물 응답을 본 뒤** 결정한다.

**전처리를 "영구히 버린다" 는 뜻은 아니다.** 타일링과 det 해상도(2500)는 PaddleX 가 긴
캔버스를 축소해 작은 글씨를 깨뜨린 실측 대응이었다. ETL 이 같은 약점을 갖는지는 모른다 —
긴 스크롤 광고 1건으로 현장에서 확인한다(현장점검 T5).

## 3. 필드 대응 — PaddleX 가 주던 것 vs ETL 이 주는 것

현재 `PaddleXPageResult` 를 소비하는 지점 기준.

| 우리가 쓰는 값 | PaddleX 출처 | ETL 대응 | 판정 |
|---|---|---|---|
| `Line.text` | `overall_ocr_res.rec_texts[]` | `paragraphs[].lines[].contents` | 대응됨 |
| `Line.bbox` | `rec_boxes` / `rec_polys` | `paragraphs[].lines[].bbox` (4점 폴리곤) | 대응됨. `_norm_bbox` 가 이미 폴리곤 처리 |
| **`Line.confidence`** | `rec_scores[]` (줄 단위) | **없음** — `confidence` 는 paragraph 단위 DLA 점수 | **결손 (G1)** |
| `LayoutBlock.label` | `block_label` (30여 종) | `paragraphs[].type` (9종) | 재매핑 필요 (G6) |
| `LayoutBlock.bbox` | `block_bbox` | `paragraphs[].bbox` | 대응됨 |
| `LayoutBlock.content` | `block_content` | `paragraphs[].contents` | 대응됨 |
| `LayoutBlock.score` | `layout_det_res.boxes[].score` | `paragraphs[].confidence` | 대응됨 |
| `RegionTable.html` | `table_res_list[].pred_html` | `paragraphs[].contents` (type=Table) | 대응됨 (`table_to_struct: html`) |
| `RegionTable.cells[].bbox` | `cell_box_list` | `cells[].bbox` | 대응됨 |
| `RegionTable.cells[].row/col` | `pred_html` 파싱으로 **추론** | `cells[].cell_info` = `[row_start, row_end, col_start, col_end]` | **개선** — 추론 불필요 |
| `n_rows` / `n_cols` | HTML 파싱 결과 | `rows` / `cols` 직접 제공 | **개선** |
| `source_width/height` | `prunedResult.width/height` | `pages[].width/height` | 좌표 스케일 필요 (G5) |

표 처리는 **오히려 나아진다**. `_build_table_grid` 는 HTML 셀 수와 좌표 수가 어긋나면
좌표를 버리는 폴백을 갖고 있는데(주석에 근거 있음), ETL 은 `cell_info` 로 행·열을
직접 주므로 그 위험이 사라진다.

### G1 을 어떻게 다룰 것인가

줄 confidence 는 우리 파이프라인에서 **세 곳**에 쓰인다. 대체안은 이렇다.

- `tiling.py:122` 중복 제거 우선순위 → **타일링을 안 하면 중복 자체가 없다.** G4 결론에
  종속된다.
- `review/export.py` 의 `needs_review` → paragraph 단위 `confidence` 를 그 영역 소속
  줄에 **상속**시키는 방식이 가장 단순하다. 다만 의미가 다르다(DLA 검출 신뢰도 ≠ 글자
  인식 신뢰도)므로 **필드명을 갈라 기록**하고 임계값은 재실측한다.
- 저신뢰 재판독 → 근거가 약해지므로, `warning_messages` 의 `USE_OCR_PAGE` 같은 신호나
  VLM Judge 결과로 후보를 고르는 쪽으로 옮기는 것을 검토한다.

**임계값 0.80 을 그대로 옮기지 않는다.** 다른 물리량이다.

### G11 을 어떻게 다룰 것인가

우리는 표 안 글자에도 OCR 오류가 있다는 실측(`'BD'`, `'2 295,000원'`)을 근거로 셀
텍스트를 정본에서 뺐다. ETL 은 표에 줄을 안 주므로 그 원칙을 유지할 수 없다.

- 1안: `cells[].contents` 를 `Line(source="ocr")` 로 올리고 **출처를 구분해 기록**한다.
  `Region.lines` 는 채워지지만 "셀에서 온 줄" 임을 잃지 않게 표시가 필요하다.
- 2안: 표 영역만 별도 판독(VLM 표 관측)으로 정본을 만든다. 이미 표 전용 VLM 관측 경로가
  있으므로 비용은 들지만 새 구조는 아니다.
- 3안: ETL 에 표 줄 단위 결과를 주는 `res_type` 이 있는지 확인한다 (질문 Q5).

**Q5 답을 받은 뒤 결정한다.** 지금 1안을 못박으면 정본 정책이 조용히 뒤집힌다.

## 5. 전환 설계

### 5.1 연결 지점은 이미 하나다

```python
# src/nh_parser/pipeline.py:154
result = request_layout_parsing(tile.image)   # 유일한 호출 지점
```

`request_layout_parsing(Image) -> PaddleXPageResult` 라는 좁은 계약 하나뿐이라
교체 자체는 어렵지 않다. 문제는 **입력 단위가 다르다**는 것이다.

```text
우리   : 타일 이미지 1장  → 동기 응답
ETL    : 파일 1건(전 페이지) → 비동기 작업
```

### 5.2 두 가지 배치 방식

**경로 A — 문서 단위 어댑터 (권장)**

원본 파일을 그대로 한 번 올리고, 돌려받은 `pages[]` 를 페이지별로 우리 IR 로 변환한다.

```text
ingest → (ETL 업로드 1회) → pages[] → paragraphs → LayoutBlock + Line → 기존 영역 조립
```

- 장점: 호출 1회. ETL 이 페이지 분리·렌더를 알아서 한다. 표 구조가 더 좋아진다.
- 대가: `make_tiles` / `dedupe_lines` / `restore_coords` 가 이 경로에서 빠진다.
  좌표 스케일 변환(G5)이 새로 필요하다.

**경로 B — 타일 이미지를 파일로 올리기 (비권장)**

기존 타일링을 유지하고 타일 1장을 1건씩 업로드한다.

- 장점: 하류 코드가 그대로다.
- 대가: 타일 수만큼 업로드+폴링이 곱해진다. 워크스페이스에 타일 이미지가 쌓인다.
  이미지 입력을 받아야만 성립한다(G2). **비용 대비 이득이 없다.**

→ **경로 A 로 간다.** 단, 긴 스크롤 광고에서 ETL 자체 렌더가 fine-print 를 깨뜨리는지
   먼저 실측해야 한다(G4). 깨진다면 그때 경로 B 또는 페이지 분할 선처리를 재검토한다.

### 5.3 파일 배치

```text
src/nh_parser/ocr/
├── paddlex.py        (유지 — 사내 실험·회귀 비교 기준선)
└── etlwithllm.py     (신설 — 클라이언트 + Default JSON → IR 변환)
```

`paddlex.py` 를 **지우지 않는다.** 전환 전후를 같은 입력으로 비교해야 회귀를 잡는다.
`.env` 로 provider 를 고르는 형태가 자연스럽다(`OCR_PROVIDER=paddlex|etl`).

### 5.4 외부 호출 vs 플랫폼 내부 이식

규격 §10 의 `custom_extension` 을 쓰면 우리 로직을 ETL 컨테이너 안에 넣을 수 있다.

| | A. 외부에서 API 호출 | B. custom_extension 이식 |
|---|---|---|
| 우리 코드 위치 | 우리 서버 | ETL 컨테이너 내부 마운트 |
| 개발·디버깅 | 지금 방식 그대로 | ETL 런타임에 종속 |
| VLM 호출 | 우리가 직접 | 플랫폼 정책에 종속 |
| 폐쇄망 배포 | ETL 주소만 있으면 됨 | 이미지·마운트 협의 필요 |
| 결과 형식 | Default JSON 을 우리가 변환 | `transform()` 에서 우리 형식 직접 생성 |

**1차 목표는 A 다.** B 는 배포 단계에서 농협이 요구할 경우의 선택지로 남긴다 —
지금 B 를 전제하면 개발 속도가 농협 환경 준비에 묶인다.

### B 를 다시 봐야 하는 이유 (2026-09-08 팀 지적)

B 를 "배포 단계 선택지" 로만 미뤄뒀는데, **G4(타일링 전제 붕괴)를 푸는 유일한 자리**일
수 있다. `custom_extension.extract(input_path, output_path, digitize_config)` 가 원본 파일
경로를 받으므로(규격 p.53), 여기서 우리 전처리(긴 캔버스 분할 등)를 그대로 살릴 수 있다.

**단, 성립 여부가 한 가지에 걸려 있다.** p.53 분기에서 `CUSTOMIZE` 는 `dla_task()` 를
부르지 않는다. 전처리 후 DLA 를 이어 부를 수 없다면 `CUSTOMIZE` 를 쓰는 순간 OCR 도
우리가 들고 들어가야 하고, 그건 "농협 OCR 을 쓰라" 는 요구와 어긋난다.

| 훅 | 전처리(DLA 전) | 후처리(DLA 후) | 확실성 |
|---|---|---|---|
| `extract()` | 가능한 자리 | — | **불확실** — DLA 로 이어지는지 미확인 |
| `transform()` | — | 가능 (`dla_result_path` 를 받는다, p.54) | 확실 |

따라서 순서는 이렇다.

1. 애자일소다에 "`extract()` 로 전처리 후 DLA 를 이어 부를 수 있는가" 를 묻는다
2. **된다면** — 플랫폼 안에서 전처리가 살아남는다. G4 가 해소되고 B 가 유력해진다
3. **안 된다면** — A(파일 단위 외부 호출)로 간다. 긴 스크롤 문제는 현장 T5 로 측정해
   대응한다

`transform()` 은 어느 쪽으로 가도 쓸 수 있다 — DLA 결과를 우리 형식으로 바꾸는 일은
플랫폼 안에서도 된다.

**현실적 문턱은 기억해 둘 것.** B 는 `docker-compose.yml` 의 `${CUSTOM_EXTENSION_PATH}`
마운트로 코드를 넣는 방식이라(규격 p.51~52) **농협 운영 컨테이너에 우리 코드를 올리는
것**이다. 보안 승인·배포 절차가 A 보다 훨씬 무겁다.

## 7. 회신 질문 초안

우선순위 순. **Q1·Q2 는 답이 없으면 개발이 멈춘다.**

> ETL with LLM API 가이드 v1.1.0 잘 받았습니다. 문서 기준으로 연동 설계를 진행하면서

> **1. 입력 파일 형식 (가장 급합니다)**
> - 가이드 예시가 모두 PDF 인데, **PNG/JPG 등 이미지 파일을 `upfiles` 로 직접 업로드**할 수 있는지요?
> - 심의 대상 광고물의 상당수가 이미지 단건으로 들어옵니다. 이미지를 지원하지 않는다면 저희가 PDF 로 변환해 올리겠습니다.
> - 지원 확장자 목록과 **파일 크기·페이지 수 상한**도 함께 알려주시면 좋겠습니다.
>
> **2. 인증**
> - `/api/v1/user/login` 이 "인증 미들웨어 설정이 필요한 경우" 로 되어 있는데, **농협 환경에서는 인증이 필수인지** 확인 부탁드립니다.
> - 필수라면 연동용 **계정 발급 절차와 필요한 권한 등급**(admin/leader/member/user), 토큰 유효기간·갱신 방식을 알려주십시오.
> - 개발·테스트용 서버 주소(IP/Port)와 워크스페이스 발급도 함께 요청드립니다.
>
> **3. 기존 Custom Parser 규격과의 관계**
> - 앞서 받은 Knowledge Lake Custom Parser 규격에는 `parser_info.prop` 으로 OCR 제공자(supplier/url/key)를 전달받는 자리가 있었습니다.
> - 이번 ETL with LLM 이 **그 자리로 들어오는 것인지**, 아니면 별도 경로로 저희가 직접 호출하는 것인지 확인 부탁드립니다.
>
> **4. 콜백 vs 폴링**
> - 저희 서버가 폐쇄망에 있을 경우 `callback_url` 수신이 어려울 수 있습니다. **폴링(1.17 파일 분석 상태 확인) 방식만으로 운영이 가능한지**, 권장 폴링 주기가 있는지 알려주십시오.
>
> **5. 요청·결과 스키마 확인 (문서 내 표기가 엇갈립니다)**
> - `tr_data` 의 **`author` 가 필수인지**. 표(p.28)에는 필수로 되어 있으나 파이썬 샘플(p.46)의 `tr_data` 에는 `author` 가 없습니다. 값이 무엇에 쓰이는지(권한·소유자 표시 등)도 알려주시면 좋겠습니다.
> - `doc_result` 하위가 `doc_result → pdfName`(p.57 표) 인지 `doc_result → default → pdfName`(p.48 예시) 인지
> - `result_doc_path` 가 문자열인지 리스트인지 (p.48 과 p.57 이 다릅니다)
> - `1.20 (by Type)` 의 `doc_path` 가 **입력 파일 경로**인지 **결과 파일 경로**인지 (p.38 URL 설명과 p.39 파라미터 설명이 다릅니다)
> - `tsr_model_name` 의 값이 `trs-sem` 인지 `tsr-sem` 인지
>
> **5-1. 표 영역의 줄 단위 결과**
> - `paragraphs[].lines` 가 "table·image·equation 외 클래스" 에만 온다고 되어 있습니다. **표 내부 텍스트를 줄 단위(좌표 포함)로 받을 수 있는 방법**이 있는지요?
> - 저희는 표 안 글자의 인식 오류를 검수하기 위해 셀 텍스트와 별개로 줄 단위 결과를 근거로 보관합니다. `cells[].contents` 외에 줄 단위를 주는 `res_type` 이나 옵션이 있으면 알려주십시오.
> - `cells[].confidence` 가 예시에서 `-1` 로 되어 있는데(가이드에도 "현재는 -1"), **실제 값이 채워질 예정인지**도 확인 부탁드립니다.
>
> **5-2. 줄 단위 인식 신뢰도**
> - `paragraphs[].confidence` 는 DLA 검출 신뢰도로 이해했습니다. **글자 인식(OCR/STR) 자체의 신뢰도를 줄 단위로** 받을 수 있는지요?
> - 저희는 인식 신뢰도가 낮은 줄만 골라 재판독하는 단계를 두고 있어, 이 값이 있으면 검수 물량을 크게 줄일 수 있습니다.
>
> **6. 오류 처리**
> - **에러 코드 정의표**를 주실 수 있는지요. 현재 가이드에서는 `0`, `-1`, `-100` 만 예시로 확인됩니다.
> - `chunk_status: "999"`(분석 오류) 일 때 **실패 원인을 조회하는 방법**이 있는지요. (`pipeline_log.log` 를 읽는 API 가 있는지)
> - 실패 시 재시도 권장 방식, 동일 파일명 재업로드 시 버전 처리 규칙도 알려주시면 좋겠습니다.
>
> **7. 품질 파라미터**
> - 작은 글씨(유의사항·심의필 문구) 인식률이 심의 정확도에 직결됩니다. `dla_score_th`/`str_score_th` 외에 **저해상도·작은 글씨 대응 옵션**이 있는지요.
> - 세로로 매우 긴 이미지(모바일 상품 상세페이지, 예: 1122×6429px)를 넣었을 때 내부적으로 축소되는지, 권장 처리 방식이 있는지 알려주십시오.
>
> **8. VLM**
> - 저희 파이프라인은 OCR 외에 **VLM(멀티모달) 판독**을 함께 사용합니다. 농협 내부에서 사용 가능한 VLM 서비스가 있는지, 있다면 규격을 받을 수 있는지 확인 부탁드립니다.
>
> **9. 성능**
> - 문서 1건당 평균 처리 시간과 **동시 요청 허용 수**를 알려주시면 배치 설계에 반영하겠습니다.
