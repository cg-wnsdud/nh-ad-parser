# 영역 분할·모델 설정 종합 진단

작성일: 2026-09-08

## 1. 결론

현재 보이는 문제를 모두 DGX Spark의 OCR/VLM 설정값 하나로 해결할 수는 없다.

- **기하학적 과병합·과분할**은 PaddleX의 요청별 레이아웃 파라미터로 개선될 수 있다.
  실제로 `1. 대출성상품.pdf`의 채권보전 주석과 부대비용이 붙은 문제는 `small`보다
  서버 기본/`large`에서 더 잘 분리됐다.
- **주석·예시가 어느 표제의 하위 내용인지**는 평면 bbox 문제가 아니라 논리적 계층과
  의미 판정 문제다. `[예금성상품-적금] 올원e적금.png`의 `주1)`, `주2)`, `예시`는
  네 가지 비교 설정 모두 별도 text 영역으로 유지됐다. 현재 구분값 라벨러는 이미지도
  받지 않으므로 들여쓰기를 볼 수 없다.
- 따라서 전 문서에 적용할 한 가지 `small`/`large` 값이나 몇 개 문서 전용 좌표 규칙을
  찾는 방식은 일반화되지 않는다. **관측 가능한 페이지 구조에 따른 요청 프로필 +
  논리적 섹션 트리 + 줄 범위 의미 라벨링**을 분리해서 설계해야 한다.
- 지금 바로 공유 서버 설정을 바꾸거나 전용 GPU를 요청할 근거는 부족하다. 우선 요청별
  프로필과 후처리를 골드셋으로 검증하고, 그래도 레이아웃 검출 자체가 반복적으로 실패할
  때 전용 PaddleX 서빙/레이아웃 모델 미세조정을 검토하는 순서가 맞다.

## 3. 현재 실제 처리 경로

```text
입력
├─ 디지털 PDF
│  ├─ pypdfium2로 텍스트 런·좌표 추출 → 텍스트 정본
│  └─ PDF 렌더 이미지 → PaddleX → 영역 bbox
├─ 스캔 PDF/PNG/JPG
│  └─ PaddleX → OCR 줄 + 영역 bbox
└─ HWP/HWPX
   ├─ 구조 파서 → 디지털 텍스트·표
   └─ 내장 이미지 → PaddleX

평면 영역/줄
└─ Gemma
   ├─ 영역 Reader/Judge(shadow일 때)
   ├─ 문서·템플릿 분류
   └─ 템플릿 구분값 라벨링
```

애플리케이션이 직접 호출하는 원격 모델 서비스는 현재 두 종류뿐이다.

- PaddleX `PP-StructureV3` 레이아웃/OCR 서비스
- OpenAI 호환 LiteLLM을 통한 Gemma VLM

`pypdfium2`는 모델이 아니라 PDF 객체·텍스트 레이어를 읽는 라이브러리다.
`ocr/etlwithllm.py`는 다른 공급자 응답용 변환기가 있으나 현재 `pipeline.py`의 실행
경로에서는 호출하지 않는다.

## 4. 디지털 PDF는 어떻게 읽는가

`1. 대출성상품.pdf`는 현재 산출물에서 다음과 같이 판정됐다.

- triage: `structured`
- 텍스트 문자 수: 1,828
- U+FFFD: 0
- 이미지 면적비: 0.005
- 최종 parse route: `hybrid`
- 해당 본문 줄의 source: `digital`

즉 드래그되는 문구의 값은 `pypdfium2`가 PDF의 TEXT 객체에서 직접 읽는다. OCR이 그
문자를 정본으로 다시 만드는 것이 아니다. 다만 영역 구조를 얻기 위해 같은 페이지를
이미지로 렌더해 PaddleX도 호출하고, 디지털 줄을 PaddleX 영역에 좌표로 배정한다. 전체
출력 모드에서는 Reader/Judge도 shadow로 실행되지만 P1의 디지털 원문은 보존한다.

이 구분이 중요한 이유는 다음과 같다.

- 글자 자체가 틀리면 PDF 텍스트 런 조립 또는 OCR 인식 문제다.
- 글자는 맞는데 다른 행/영역에 붙으면 레이아웃·줄 귀속·논리 구조 문제다.
- 대출 PDF의 r025는 두 번째에 해당한다. OCR 인식 모델을 바꿀 문제가 아니다.

## 5. 두 문제 문서의 원인

### 5.1 올원e적금: 영역보다 부모-자식 관계 문제

`우대이율 안내` 다음의 `최고 연 3.6%p`, 조건 ①~③, `주1)`, `주2)`, `예시`는 시각적으로
다음 `상품 안내` 표제가 나오기 전까지 한 섹션이다. 그러나 PaddleX 결과는 이들을 각자
평면 text bbox로 반환한다. 비교한 네 설정 모두 `주1)`, `주2)`, `예시`를 별도 bbox로
유지했다.

현재 구분값 라벨러의 입력에는 각 영역의 텍스트, layout label, score, bbox 숫자만 있고
페이지 이미지가 없다. 프롬프트에는 섹션 표제의 범위, 각주 표식 연결, 들여쓰기 계층을
계승하라는 규칙도 없다. 이 때문에 VLM이 `주1)`/`주2)`를 일반적인 유의사항으로 분류한
것은 레이아웃 모델 설정만으로 고칠 수 없다.

필요한 것은 텍스트 소유권을 억지로 한 bbox에 합치는 것이 아니라 다음 관계를 보존하는
논리 구조다.

```text
section: 우대이율 안내
├─ 우대금리 요약
├─ 우대조건 ①
├─ 우대조건 ② ── footnote_ref: 주1
├─ 우대조건 ③ ── footnote_ref: 주2
├─ footnote 주1
├─ footnote 주2
└─ example
```

이 트리에서 `주1`, `주2`, `예시`는 별도 영역으로 유지하되 `우대금리` 섹션을 상속하면
P3의 원문 소유권과 의미 소속을 동시에 보존할 수 있다.

### 5.2 대출 PDF: 실제 과병합 + 라벨러 미활용 문제

이 문서는 한 타일로 처리되므로 타일 겹침 200/400은 해당 문제에 영향을 주지 않는다.

- 현행 `small`: 채권보전 주석과 부대비용 두 항목이 r025 하나로 합쳐졌다.
- 서버 기본 미지정 및 `large`: `무입보신용 + 요양급여비 주석`과 `부대비용`이 서로
  다른 영역으로 나뉘었다.

따라서 이 자리는 요청별 bbox 필터 모드가 실제로 개선할 수 있는 기하 문제다. 다만
`large`를 전역 기본으로 바꾸면 사진형 카드 콜라주처럼 큰 바깥 bbox가 작은 의미
영역들을 삼키는 회귀가 이미 관측됐다.

또한 현재 P3 스키마는 한 영역에 여러 라벨과 줄 범위(span)를 붙일 수 있다. 설령 r025가
물리적으로 하나여도 첫 줄은 `채권보전`, 뒤의 두 항목은 `부대비용`으로 나눠 전달할 수
있다. 그런데 현 라벨러는 r025 전체를 미라벨로 남겼다. 그러므로 기하 분리 개선과 별개로
줄 범위 의미 라벨러도 보강해야 한다.

이 PDF에는 행을 가르는 가로 벡터 선과 왼쪽 행 표제가 있다. 현재 PDF 구조 파서는
텍스트 줄 조립을 위해 세로 구분선만 활용한다. 정형 표형 PDF에서는 가로 구분선과 왼쪽
표제 앵커를 행 경계로 쓰는 것이 특정 문구 정규식보다 일반화 가능성이 높다.

## 6. 현재 서버와 요청 설정

### 6.1 PaddleX API에서 오늘 직접 확인한 것

`GET /paddlex/openapi.json`의 `InferRequest`에는 39개 필드가 있다. 현재 health는
`Healthy`였다.

아무 옵션도 지정하지 않은 최소 추론에서 응답이 보고한 기본값은 다음과 같다.

```text
use_doc_preprocessor=false
use_seal_recognition=false
use_table_recognition=true
use_formula_recognition=false
use_chart_recognition=false
use_region_detection=true
format_block_content=false
use_textline_orientation=true

text detection:
  limit_side_len=736
  limit_type=min
  thresh=0.3
  max_side_limit=4000
  box_thresh=0.6
  unclip_ratio=1.5
text_rec_score_thresh=0
```

현재 애플리케이션 요청은 주로 다음 값을 덮어쓴다.

```text
useDocOrientationClassify=false
useDocUnwarping=false
textDetLimitSideLen=2500
textDetLimitType=max
layoutMergeBboxesMode=small
useFormulaRecognition=false
useTextlineOrientation=false
```

같은 요청의 응답에서 `2500/max`, detector threshold `0.3/0.6`, unclip `1.5`, 방향분류
`false`가 실제 적용된 것을 확인했다. 요청 본문의 추론 옵션은 그 호출에만 적용되므로
공유 서버 설정을 바꾸지 않는다.

공식 문서에 따르면 요청별로 바꿀 수 있는 레이아웃 핵심 옵션은 다음과 같다.

- `layoutThreshold`: 전체 또는 클래스별 score threshold
- `layoutNms`: NMS 사용 여부
- `layoutUnclipRatio`: bbox 확장 비율
- `layoutMergeBboxesMode`: `large`, `small`, `union` 또는 클래스별 값
- `textDet*`, `textRecScoreThresh`: 글자 검출·인식 후처리 값

공식 문서의 의미상 `union`은 좌표를 하나로 합치는 것이 아니라 중첩된 큰/작은 bbox를
둘 다 유지하는 모드다. 다만 현재 코드는 `parsing_res_list`를 우선해 영역을 만들기 때문에
`layout_det_res`에 추가로 남은 후보를 그대로 활용하지 않는다. `union` 요청만 켜서는
기대 효과가 P3까지 자동 전달되지 않는다.

### 6.2 Gemma API에서 오늘 직접 확인한 것

LiteLLM 버전은 API 문서상 1.95.0이고 현재 `/models`에는 두 별명이 노출된다.

- `spark-gemma-4-26b-NVFP4-MTP` — 현재 `.env`가 사용하는 모델
- `b200-gemma-4-26b-NVFP4-MTP`

`/model/info`에서 두 별명 모두 backend model 문자열은
`openai/gemma-4-26b-NVFP4-MTP`로 확인됐다. Spark 별명은 내부 vLLM, B200 별명은 별도
NHN Cloud 엔드포인트로 라우팅된다. 과도한 `max_tokens` 요청의 오류 메시지에서 Spark
모델 그룹의 `max_total_tokens=131072`를 확인했다.

게이트웨이의 `ProxyChatCompletionRequest`는 `temperature`, `top_p`, `seed`, `n`,
`logprobs`, `top_logprobs`, `response_format`, `max_tokens` 등을 요청별로 받는다. 현재
클라이언트는 다음만 보낸다.

```text
model=<.env GEMMA_MODEL>
temperature=0
max_tokens=<태스크별 값>
messages=...
response_format=json_schema(strict=true)
```

seed/logprobs/n 등은 현재 운영 호출에 쓰이지 않는다. API 스키마에 존재한다는 것과 특정
백엔드에서 원하는 효과가 난다는 것은 별개이므로 골드 기반 재현성 실험 없이 품질 개선을
주장해서는 안 된다.

### 6.3 API만으로 확정할 수 없는 현재 모델 정보

PaddleX 응답은 활성 스위치와 detector 파라미터는 보여 주지만 서브모델 이름, 가중치
해시, 전체 레이아웃 클래스 표, 서버 YAML은 보여 주지 않는다. 이전 SSH 실사 기록에는
다음 구성이 적혀 있다.

- layout: `PP-DocLayout_plus-L`
- document region: `PP-DocBlockLayout`
- text detection: `PP-OCRv5_server_det`
- text recognition: `korean_PP-OCRv5_mobile_rec`
- orientation: `PP-LCNet_x1_0_textline_ori`
- table: `SLANeXt_wired`, `SLANet_plus`, RT-DETR-L cell detectors
- disabled optional modules: seal, chart, formula, document preprocessing

오늘의 API 응답은 활성/비활성 스위치와 text detector 기본값에 대해서는 이 기록과
일치한다. 정확한 모델 이름·버전까지 “현재도 동일하다”고 확정하려면 SSH 또는 운영자
출력이 필요하다.

## 7. 이전 조사에서 수정해야 할 해석

### 7.1 88%는 정확도의 절대 천장이 아니다

PaddleOCR 공식 문서의 `88.0%`는 5,007개 이미지로 구성된 특정 Korean Dataset의
benchmark다. 모델·도메인 전체의 절대 정확도 천장이 아니다. 최신 PaddleX 문서는 같은
이름의 모델에 90.45%도 제시한다. 서버의 실제 가중치 버전과 우리 광고 골드셋 평가 없이
“88%가 천장”이라고 말하면 안 된다.

### 7.2 클래스별 dict 동작은 아직 검증되지 않았다

파라미터 프로브에서 `{'2':'large'}`, `{'1':'large','2':'large'}`, 존재하지 않는
`{'999':'large'}`가 같은 fingerprint를 냈다. 공식 문서는 dict key를 class ID라고
설명하지만, 현재 서버 래퍼의 JSON key 변환/미지정 클래스 fallback이 어떻게 동작하는지는
이 실험으로 확인되지 않았다. “필요한 클래스만 덮어쓰기 가능함을 실측 확인”이라는 결론은
보류해야 한다.

### 7.3 비교 실험은 완전한 요인 분리가 아니다

현재 네 설정은 다음과 같다.

- baseline: small + overlap 200
- server: merge 미지정 + overlap 200
- candidate: large + overlap 400
- small400: small + overlap 400

`small`의 overlap 효과는 baseline/small400으로, overlap 400에서 merge 효과는
small400/candidate로 볼 수 있다. 그러나 server default와 explicit large를 같은 overlap로
직접 비교하는 `large200`, 그리고 `union200`이 없다. 또한 비교 JSON은 애플리케이션의
parse 결과이지 PaddleX 원응답 전체가 아니다.

### 7.4 영역·줄 수는 정확도 지표가 아니다

7문서에서 `small`은 대체로 영역 수를 늘리고 `large`/server는 줄였지만, 어느 쪽이
정답인지는 수로 결정할 수 없다. 대출 PDF의 문제 행에서는 large가 낫고, 카드 콜라주에는
small이 낫다는 반대 사례가 이미 있다. 사람의 boundary/parent/label 골드가 필요하다.

## 8. 앞으로 불필요한 작업을 줄이는 구현 순서

### 8.1 먼저 작은 골드셋을 만든다

30~50문서를 다음 축으로 층화한다.

- 디지털 PDF / 스캔 PDF / 긴 모바일 이미지 / 카드 콜라주 / 표형 문서
- 예금성 / 대출성 / 카드 / 투자성
- 단일 상품 / 다상품

각 문서에서 모든 bbox를 새로 그릴 필요는 없다. 오류가 발생한 지점에 다음만 표시해도
파라미터 선택에 충분하다.

- 올바른 물리 영역 경계 또는 `keep separate`
- 부모 section/heading ID
- 각주·예시의 대상 ID
- 줄별 템플릿 구분값
- 텍스트 정본 출처(digital/OCR/VLM)와 검수 필요 여부

평가 지표도 분리한다.

1. 텍스트 누락/오인식
2. bbox 과병합/과분할
3. section·footnote 관계
4. 줄 범위 구분값 precision/recall
5. P3 검수 필요율, 호출 수, 시간

### 8.2 공유 서버를 유지하고 요청 프로필을 만든다

문서 이름이 아니라 관측 가능한 구조로 프로필을 선택한다.

- 긴 이미지·카드 콜라주: `small` 후보
- 디지털 PDF의 행 구분 표형 레이아웃: server/`large`/`union` 후보
- 중첩 bbox가 많은 페이지: `union` 원후보를 받아 클라이언트에서 선택

프로필은 CLI 또는 요청 객체로 명시하고 P1에 실제 payload/profile ID를 기록해야 한다.
그러면 같은 입력을 재현할 수 있고 공유 서버에는 영향이 없다. 전역 기본값을 성급히
바꾸지 않는다.

### 8.3 평면 regions 위에 논리 구조 계층을 추가한다

물리 bbox와 의미 소속을 하나로 만들지 않는다. 예를 들면 다음 필드를 별도 계층에 둔다.

```json
{
  "region_id": "p1_r016",
  "parent_section_id": "p1_s005",
  "relation": "footnote",
  "refers_to": ["p1_r014"],
  "indent_level": 2
}
```

입력 종류별로 사용할 근거는 다음과 같다.

- 공통: 제목 bbox, y 순서, x 들여쓰기, 글머리 기호, 각주 번호, 다음 제목까지의 범위
- 디지털 PDF: 폰트 크기/굵기, PDF 텍스트 런, 가로·세로 벡터 구분선
- 이미지: PaddleX bbox와 필요시 VLM 시각 판정

### 8.4 구분값 라벨러를 section-aware로 바꾼다

현재 텍스트 전용 10영역 배치에는 다음 보강이 우선이다.

- 각 영역에 `parent heading`, 앞뒤 이웃, relation을 함께 제공
- 배치 경계에서 섹션이 끊기지 않도록 section 단위 배치 또는 context overlap 사용
- 템플릿 예시뿐 아니라 설명, 포함 범위, 다른 라벨과의 구별 기준 제공
- 혼합 영역은 영역 전체가 아니라 기존 span 기능으로 줄별 라벨 지정
- bbox/들여쓰기가 실제 판단 근거일 때만 이미지 crop을 추가하고, 모든 영역에 무조건
  VLM 이미지를 붙여 비용을 늘리지 않음

### 8.5 그 뒤에 모델/전용 GPU를 판단한다

다음 조건이면 전용 PaddleX 서빙 또는 레이아웃 모델 미세조정이 합리적이다.

- 요청 프로필과 구조 후처리 후에도 같은 유형의 경계 누락이 골드셋에서 반복됨
- 필요한 영역 클래스가 현재 20-class ontology에 없음
- 공유 서버 부하 때문에 실험/운영 SLA를 맞출 수 없음
- 학습할 bbox·class annotation이 충분히 축적됨

전용 서빙은 공유 서버를 수정하는 것이 아니라 새 endpoint로 만들어야 한다. 첫 버전은
기존 모델과 YAML을 복제하고 설정·모델 hash·컨테이너 digest를 고정한 뒤, 레이아웃
모델/설정만 한 번에 하나씩 바꿔 비교한다. 글자 인식 오류가 아닌 영역 오류를 고치려고
OCR recognition 모델부터 학습하는 것은 우선순위가 아니다.

전용 VLM은 다음이 입증될 때 검토한다.

- 이미지 crop을 올바르게 줘도 작은 글자/관계 판정이 반복적으로 실패함
- 현재 양자화·이미지 토큰 예산·동시 배치의 변동성이 품질/SLA 병목임

그 전에 이미 등록된 Spark/B200 두 별명을 같은 저장 파싱 결과와 같은 프롬프트로 A/B해
백엔드 차이가 실제 품질 차이인지 확인하는 편이 GPU 요청보다 싸다.

## 9. 현재 추가로 필요한 서버 접근 정보

오늘 `10.90.0.103` SSH 접속은 `Permission denied (publickey,password)`로 실패했다.
다음 중 하나가 있으면 현재 모델 구성을 완전히 확정할 수 있다.

- 읽기 전용 SSH 계정/키
- 또는 운영자가 아래 명령의 출력을 전달

```bash
docker inspect paddle-structurev3 --format '{{json .Config.Image}} {{json .Config.Cmd}}'
cat /data/rookies-lab/paddlex-service/configs/PP-StructureV3.yml
docker exec paddle-structurev3 python -m pip show paddlex paddleocr paddlepaddle-gpu
find /data/rookies-lab/paddlex-service/paddlex-model-cache/official_models -maxdepth 2 -type f
docker logs vllm 2>&1 | grep -E 'non-default|max-model-len|quant|kv-cache|mm-processor|speculative'
curl -s 127.0.0.1:8102/v1/models
nvidia-smi
```

특히 필요한 값은 PaddleX 클래스 label map, 클래스별 threshold/merge dict, 모델 디렉터리
및 가중치 hash, 컨테이너 digest, vLLM의 정확한 기동 인자다.
