# spark-1118 OCR 기반 파싱 파이프라인 고도화 계획

## 1. 이번 결정

- OCR·레이아웃: spark-1118의 PaddleX PP-StructureV3
- PaddleX 실행 설정: HTTP에서 선택 옵션을 보내지 않고 spark-1118 파이프라인 YAML만 사용
- VLM: 기존 fc87 Gemma 호출 경로(`GEMMA_URL`, `GEMMA_MODEL`)
- 일반 비율 페이지: 페이지 전체를 한 번 호출
- 긴 페이지: 글자 밀도 밴드로만 분할한 뒤 페이지 좌표 복원·중복 제거
- 최종 계약: 기존 P1/P3의 페이지→Region 구조를 유지한다. `FieldRow` 같은 새 최종
  계층은 만들지 않되 Region/P3 scope에 `product_id`를 추가하고 라벨은 Region당 하나로 단순화한다.

`layout-20260918-v1--merge-large`에서 실제로 보낸 요청은 다음과 같았다. 이는 설정 비교를
위한 과거 실행이며, 새 파이프라인의 운영 요청으로 사용하지 않는다.

```json
{
  "fileType": 1,
  "useDocOrientationClassify": false,
  "useDocUnwarping": false,
  "useFormulaRecognition": false,
  "useTextlineOrientation": false,
  "useTableRecognition": false,
  "layoutMergeBboxesMode": "large"
}
```

새 파이프라인은 아래처럼 필수 형식값만 보내고, merge·threshold·unclip·text detection과
모듈 on/off는 전부 spark-1118 YAML에서 읽는다.

```json
{"fileType": 1}
```

따라서 이후 설정 변경은 서버 YAML 한 곳에서 수행한다. 실행 manifest에는 실제 요청과
`paddlex_options_source=server_pipeline_yaml`을 기록해 요청 override가 다시 들어오는 것을
검출한다.

## 2. 기존 파이프라인이 현재 하는 일

```text
파일 입력
  → 이미지 로드 / PDF 렌더 / HWP 자산 추출
  → PDF 페이지 triage + 선택 가능한 디지털 텍스트 추출
  → 높이 4000px 초과 시 타일링
  → PaddleX 호출
  → 타일 좌표를 페이지 좌표로 복원
  → OCR 줄·레이아웃 블록 중복 제거
  → parsing_res_list를 Region으로 만들고 OCR/디지털 줄 배정
  → 미배정 줄을 인접 Region에 흡수
  → 카드/패널 VLM 그룹핑
  → 읽기 순서 최소 교정
  → 영역 Reader/Judge + 페이지 누락 문구 sweep
  → 문서 상품군·상품명 노출 여부 분류
  → 19개 템플릿 중 하나 선택
  → Region 줄 범위에 템플릿 구분값 라벨 부착
  → P1 전체 근거 + P3 심의 입력 생성
```

| 기존 코드 | 재사용 이유 |

| `layout.regions.build_regions` | 줄 면적 50% 이상 겹침, 동률이면 작은 영역 우선이라는 단일 귀속 원칙이 있다 |

## 3. 새 실험 파이프라인의 디렉터리와 경계

우선 `experiments/parser-v2/`에서 실행하되, 검증된 함수는 `src/nh_parser`에서 가져다 쓴다.
기존 코드를 통째로 복사하지 않는다.

```text
experiments/parser-v2/
  run.py                 단계 실행기
  config.py              1118 OCR / fc87 VLM 실행 프로필
  adapters.py            새 OCR 결과 → AdDocument/AdPage/Region 변환
  stages/
    ownership.py         상품/패널 소유권 그룹

    ordering.py          그룹 안 읽기 순서
  outputs/<run>/
    00-input.json
```

각 단계 산출물을 따로 남겨야 문제가 OCR, 좌표 복원, 줄 귀속, 상품 그룹, VLM 중 어디서
생겼는지 구분할 수 있다.

## 4. 단계별 구현

### 단계 0. 실행 프로필 고정

OCR과 VLM 주소는 한 프로세스에서 서로 독립된 환경변수를 쓴다.

```text
PADDLEX_URL=http://127.0.0.1:18081/layout-parsing   # 1118 SSH 터널
GEMMA_URL=<기존 fc87 Gemma URL>
GEMMA_MODEL=<기존 Gemma 모델명>
```

엔드포인트는 코드에 쓰지 않고 `.env` 또는 실행 시 환경변수로만 둔다. 각 실행은 실제
요청 payload와 모델명을 manifest에 기록한다.

**완료 조건**: manifest의 PaddleX 요청이 `{"fileType": 1}`이고, 서버 YAML을 바꾸지 않은
반복 실행의 `2-parsing`, `3-ocr`가 일치한다.

### 단계 1. 입력과 타일링을 통합

1. PNG/JPG는 원본 픽셀을 사용한다.
2. PDF는 기존 렌더·triage를 사용한다.
3. `max(width, height) / min(width, height) <= 2.0`이면 통짜 한 번 호출한다.
4. 2.0을 넘으면 기존 `content_bands`로 글자량을 균등하게 나누고 빈 줄에 컷을 스냅한다.
5. 기본 목표 span은 1600px, overlap은 15%(80~200px)로 둔다.
6. 타일 결과에 원본 좌표 offset과 piece ID를 붙이고, 서로 다른 타일에서 나온 중복만 제거한다.
7. 같은 타일 안의 중첩 박스는 계층 구조일 수 있으므로 제거하지 않는다.

일반 페이지와 긴 페이지 모두 이후 단계에는 동일한 **페이지 좌표계** 결과를 넘긴다. 이후
후처리는 통짜였는지 타일이었는지 몰라도 동작해야 한다.

**완료 조건**: 통짜 페이지는 호출 1회, 긴 페이지는 모든 박스가 원본 캔버스 안에 있고
타일 경계 OCR 줄·레이아웃 블록 중복이 없다.

### 단계 2. 원본 관측을 보존

페이지마다 다음 세 목록을 수정하지 않고 저장한다.

- `layout_det_res`: 점수 있는 검출기 후보
- `parsing_res_list`: PaddleX가 정리한 영역 후보
- `overall_ocr_res`: 모든 OCR 줄

PaddleX가 붙인 `table`, `text`, `paragraph_title` 등의 이름은 **관측값**이지 NH 업무 의미의
정답으로 사용하지 않는다.

**완료 조건**: 어떤 후처리 결과든 원본 응답과 좌표까지 역추적할 수 있다.

### 단계 3. Region 본문 후보와 줄의 단일 소유권

#### 왜 `block_content`와 OCR 줄을 둘 다 보존하나

2026-09-18 `merge-large` 51페이지 실측 결과는 다음과 같다. 아래 수치는 HTTP scalar
override를 사용한 과거 기준선이므로 서버 YAML 기준 재실행 수치와 분리해서 본다.

| 항목 | 결과 |
|---|---:|
| `parsing_res_list` Region | 1,206개 |
| `block_content`가 비어 있음 | 47개 |
| 빈 Region인데 배정 가능한 OCR 줄이 있음 | 31개 |
| `table` Region | 31개 모두 `block_content`가 비어 있음 |
| `block_content`는 있지만 배정 OCR 줄이 없음 | 14개 |
| 두 후보가 모두 있고 문자열 유사도 0.8 이상 | 997/1,145개(87.1%) |
| 문자열 유사도 0.5 미만 충돌 | 24개 |
| 같은 페이지 안 중복 `block_content` 그룹 | 11개(22 Region) |

따라서 `block_content`만 쓰면 표 31개를 포함한 빈 본문을 잃고, OCR 줄만 다시 조립하면
PaddleX가 정리한 블록 순서와 본문을 불필요하게 버린다. 새 기준은 다음 혼합 방식이다.

1. `block_content`를 PaddleX 본문 후보로 보존한다.
2. OCR/디지털 줄은 좌표·신뢰도·line ID를 가진 독립 후보로 Region에 한 번만 귀속한다.
3. 선택 가능한 PDF 텍스트가 있으면 디지털 줄을 우선하고, 디지털 박스가 덮지 못한 OCR 줄만 보충한다.
4. `block_content`가 비면 줄 후보로 보완한다.
5. 문자열 유사도 0.5 미만처럼 두 후보가 크게 다르면 어느 쪽도 조용히 폐기하지 않고
   후속 라벨링 VLM/Judge 입력에 함께 넣는다. 0.5~0.8 차이는 기록하되 별도 호출을 만들지 않는다.

이 비교는 같은 PaddleX 응답 안의 두 목록을 쓰므로 추가 모델 호출이나 GPU 추론 비용이 없다.

1. Region 후보는 우선 `parsing_res_list`를 사용한다.
2. 각 OCR/디지털 줄은 줄 면적 50% 이상을 담는 Region만 후보로 본다.
3. 여러 Region이 줄을 담으면 겹침비가 큰 쪽, 동률이면 면적이 작은 구체적 Region을 고른다.
4. 각 출처의 줄은 정확히 한 Region 또는 `unassigned_lines` 한 곳에만 존재해야 한다.
5. 큰 부모 Region 안의 작은 Region을 바로 삭제하지 않는다. `parent_id/child_ids` 같은 내부
   관계만 기록하고, 텍스트 소유권은 작은 Region에 한 번만 둔다.
6. 첫 구현에서는 현재의 넓은 최근접 흡수를 끈다. 미배정은 손실이 아니라 진단 가능한 상태다.

**완료 조건**:

- OCR/디지털 정본 줄의 누락 0건
- 중복 소유 0건
- 서로 다른 상품이나 행의 줄이 근접 흡수 때문에 합쳐진 사례 0건

### 단계 4. 상품·패널 소유권

Region은 모델이 찾은 시각 블록이고, 상품 그룹은 NH 업무 소유권이다. 둘을 같은 것으로 보지
않는다. 원본 Region은 유지하고 각 Region에 `product_id`를 붙인다.

1. 좌우 열, 큰 외곽 테두리, 배경색, 패널 사이 여백으로 결정론 후보를 만든다.
2. 후보가 둘 이상일 때만 페이지 이미지와 Region 목록을 Gemma에 보내 판정한다.
3. 각 Region을 상품 1, 상품 2 또는 페이지 공통(header/notice)으로 배정한다.
4. 긴 스크롤 페이지는 기본적으로 한 상품 흐름으로 보고 카드 collage VLM 호출을 하지 않는다.
5. 기존 `assign_cards_vlm`의 좌표·밀도 힌트와 다수결 아이디어는 참고하되, 새 출력에는
   `card_no`를 사용하지 않고 일반적인 상품 소유권만 기록한다.

각 Region에 `product_id`를 직접 둔다. 한 페이지 안에서 상품은 `p1_product_01`,
`p1_product_02`처럼 안정된 문자열 ID를 사용한다. 여러 상품에 공통인 제목·고지문은
`product_id=null`로 두고 `ownership_status=page_common`으로 구분한다. P3에는
`scope.product_id`로 내보내며 `card_no`는 만들지 않는다. 여러 페이지에 같은 상품이
이어지는 실제 입력이 확인되면 문서 단위 ID로 승격한다.

**완료 조건**: 여러 상품 페이지에서 한 상품의 Region이 다른 상품 그룹으로 넘어가지 않고,
공통 제목·고지문은 특정 상품에 억지로 붙지 않는다.

### 단계 5. 그룹 안 읽기 순서

1. 문서 전체를 y순으로 정렬하지 않는다.
2. 먼저 상품/패널 그룹 순서를 정한다.
3. 그룹 안에서 PaddleX 순서를 기준으로 두고, 확실히 뒤집힌 이웃만 기존
   `repair_reading_order`로 교정한다.
4. Region 안 OCR 줄은 기존 `sort_reading_order`로 같은 시각 행을 묶고 좌→우로 정렬한다.
5. 항목 값이 여러 Region으로 갈린 경우 Region을 파괴적으로 합치지 않고 같은 그룹 안에서
   연속 순서를 보존한다.

**완료 조건**: 좌우 상품 문장이 번갈아 나오지 않고, 한 상품 안에서는 항목 제목 다음에 그
항목 값이 이어진다.

### 단계 6. 미배정 줄의 제한적 회수

미배정 줄은 다음 순서로만 회수한다.

1. Region 내부에 중심점이 들어가는 줄
2. 같은 상품 그룹 + 같은 열 + 사이에 다른 Region/구분선 없음
3. 위 조건을 만족하면서 가까운 줄
4. 그 외는 미배정 유지

현재 `_absorb_unassigned_into_regions`의 `max(300px, 페이지 높이 15%)` 근접 규칙은 긴
페이지에서 다른 항목으로 넘어갈 수 있으므로 그대로 사용하지 않는다. 미배정 줄도 P3까지
전달되므로 억지로 붙이는 것보다 안전하다.

**완료 조건**: 의미 있는 미배정 줄 수는 줄되 상품·행 경계를 넘긴 흡수는 0건이다.

### 단계 7. fc87 Gemma 영역 판독과 페이지 문맥

기존 `vlm.client.chat_json`, 이미지 인코딩, JSON schema, 캐시를 재사용한다.

1. Region 또는 처리 그룹 crop과 OCR/디지털 정본을 준비한다.
2. 기존 `adjudicate_regions_shadow`처럼 VLM 판독을 별도 후보로 저장한다.
3. OCR 정본을 VLM 결과로 즉시 덮어쓰지 않는다.
4. 표처럼 보이는 영역은 표 전용 Reader로 행/셀 구조를 관측한다. PaddleX의 `table` 라벨은
   Reader 선택의 힌트일 뿐 최종 판정 근거로 사용하지 않는다.
5. 페이지 sweep은 `3-ocr`에도 없는 시각 문구 탐색에만 사용한다. 찾은 문구는
   `RecoveryCandidate`로 남기고 자동 정본으로 편입하지 않는다.
6. 첫 비교는 `REGION_READING_MODE=shadow`, `REGION_READING_SCOPE=all`로 실행한다. 품질을
   확인한 뒤 안전한 영역만 호출하는 `targeted` 모드로 비용을 줄인다.

포스터형 일반 페이지는 페이지 전체 이미지도 Gemma에 한 번 제공한다. 모델이 좌표를 새로
그리게 하지 않고 `region_id`, `product_id`, 정규화 bbox, OCR/디지털 텍스트 요약을 이미지와
함께 준다. Gemma는 제공된 ID만 선택할 수 있다. 긴 페이지는 전체 이미지를 작은 글씨
판독용으로 쓰지 않고 저해상도 overview는 문맥용으로만 주며, 실제 판독은 상품 그룹 또는
밴드 crop으로 한다.

페이지 전체 이미지·좌표 목록과 이 문맥 판독의 예시 응답은 **라벨 정확도를 높이기 위한
실행 중 입력**이다. 독립적인 업무 산출물이나 P3 필드로 남기지 않는다. 재현이 필요할 때만
gitignore 대상 실행 trace에 보존하고, 최종 산출물에는 확정 라벨·신뢰도·검수 필요 여부만 남긴다.

**완료 조건**: VLM 후보가 다른 Region 문구를 삼키지 않고, OCR과 불일치하는 숫자·금리·기간은
검수 대상으로 남는다.

### 단계 8. 문서 분류와 템플릿 선택

기존 흐름을 그대로 사용한다.

1. 첫 페이지 이미지 + 파일명으로 상품군, 광고 유형, 상품명 노출 여부를 Gemma로 관측
2. `resolve_template`가 규칙으로 후보를 줄이고 필요할 때만 Gemma로 19개 중 하나를 선택
3. 템플릿을 확정하지 못하면 임의 선택하지 않고 `unresolved`로 남김

여러 상품이 있어도 같은 광고 템플릿을 따르는 문서라면 문서당 템플릿 하나를 유지한다.
서로 다른 상품군이 한 문서에 있는 실제 입력이 확인될 때만 그룹별 템플릿 확장을 검토한다.

### 단계 9. 템플릿 구분값 단일 라벨링

기존 `label_regions`의 템플릿 enum·정의 생성 부분은 재사용하지만 출력 계약은 v2로 바꾼다.

- 선택 템플릿의 구분값 enum 밖 라벨은 만들 수 없다.
- 일반 페이지는 페이지 전체 이미지, Region ID/bbox/text, 상품 group을 한 요청에 넣어 위치와
  주변 문맥을 함께 본다.
- 각 텍스트 Region에는 주 라벨 하나만 둔다. `line_from/line_to` span은 만들지 않는다.
- 라벨의 근거는 Region이 이미 소유한 전체 `line_refs`다.
- 명시적 항목명과 고정 문구 규칙이 Gemma 오분류를 교정한다.
- `product_id`를 프롬프트에 함께 넣어 다른 상품의 영역을 섞지 않게 한다.

한 Region에 실제로 여러 템플릿 구분값이 섞여 있으면 하나를 임의로 고르지 않는다. 내부
응답을 `needs_split=true`로 기록해 Region 분할 단계로 되돌리거나 검수 대상으로 남긴다.
최종 P3에는 확정된 주 라벨 하나 또는 라벨 없음만 허용한다.

이 기준 때문에 Region 경계의 목표가 더 분명해진다.

1. 서로 다른 상품이 한 Region에 섞이지 않음
2. 상품 설명과 고지문이 한 Region에 섞이지 않음
3. 템플릿 구분값 하나로 설명할 수 있는 의미 단위임

### 단계 10. 기존 P1/P3로 export

`build_evidence`와 `build_review_input`의 원문 보존·line_ref 소유권 검사는 그대로 사용하고,
Region 단일 라벨과 `product_id`를 내보내는 부분만 확장한다.

- P1: OCR/디지털 원문, VLM 후보, Judge, bbox, 라벨 근거를 모두 보존
- P3: Region마다 하나의 선택 텍스트, 원문 line refs, `product_id`, 주 템플릿 라벨 하나,
  검수 필요 여부
- 모든 입력 줄은 P3의 Region 또는 미배정 텍스트에 정확히 한 번 존재해야 함

새 전처리·OCR·그룹핑 결과를 기존 `AdDocument` 계약으로 바꾸는 adapter를 만들고, review
export에는 선택 필드 두 개(`product_id`, 단일 `label`)만 추가한다. 페이지→Region→텍스트라는
심의 입력의 큰 구조는 다시 설계하지 않는다.

### 단계 11. 심의 결과와 화면 하이라이트 연결

VLM이나 심의 모델이 bbox 숫자를 새로 만들게 하지 않는다. P3의 각 Region은 안정적인
`region_id`, `page_no`, 원본 페이지 bbox, canvas 크기를 갖고, 심의 결과는 판단 근거로 사용한
`evidence_region_ids`만 반환한다. 화면 API가 그 ID를 P3에서 찾아 실제 bbox 목록으로 바꾼다.

- 본문과 유의사항처럼 한 판정이 여러 Region을 사용하면 여러 bbox를 함께 하이라이트한다.
- 미배정 줄은 bbox를 버리지 않는다. 복구 Region으로 승격되지 않아도 P3 진단 항목에 bbox를 남긴다.
- VLM sweep의 근사 bbox는 `bbox_quality=coarse`, OCR/PDF 좌표는 `exact`로 구분한다.
- `위반`, `판정불가`, `충족` 모두 같은 근거 ID 계약을 사용한다.

### VLM 호출 위치와 예상 횟수

상품 소유권, 미배정 후보 처리, 단일 템플릿 라벨을 각각 별도 호출하지 않는다. 같은 페이지
문맥 판독 응답을 세 단계가 재사용한다.

| VLM 단계 | 호출 조건 | 현재 51페이지 예상 |
|---|---|---:|
| 문서 분류·템플릿 선택 | 파일명·결정론 규칙으로 확정되지 않은 문서만 | 문서당 0~1회, 최대 49회 |
| 페이지 문맥 판독 | 상품 소유권 + 복구 후보 조치 + Region 단일 라벨을 한 응답에서 판정 | 일반 44페이지 44회 + 긴 7페이지 각 2~4회 = **58~72회** |
| 누락 문구 sweep | 위 페이지 문맥 응답에 함께 포함. 정말 OCR 줄이 없는 후보만 후속 crop OCR | 별도 VLM 호출 0회가 목표 |
| Region Reader | 서버 본문과 OCR/PDF 정본이 크게 다르거나 금리·금액 등 중요 영역만 | 현재 충돌 상한 85회, 필터 후 목표 20~50회 |
| Judge | Reader와 정본이 실제로 다를 때만 | Reader 불일치 수만큼, 0~50회 예상 |

첫 구현은 페이지 문맥 판독까지 붙이고 Reader/Judge는 shadow로 제한한다. 호출 수는 실행
manifest에 단계별로 기록하고, 같은 이미지·프롬프트는 기존 VLM 캐시를 사용한다.

## 6. 설정 선택 및 품질 우선순위

자동 점수와 사람 검토의 우선순위는 다음과 같다.

1. 서로 다른 상품·고지문·행 내용 혼합 건수
2. 상품 그룹 소유권 오류 건수
3. 중요한 OCR/디지털 줄 누락 건수
4. 같은 줄의 중복 소유 건수
5. 영역 파편 수와 VLM 호출 수
6. 전체 latency와 메모리

박스 수가 적거나 미배정 줄이 적다는 이유만으로 품질이 좋다고 판정하지 않는다. 서버 YAML의
클래스별 merge 설정이 앞의 1~4 조건을 만족하는지 먼저 평가하고, 변경은 YAML에서만 한다.

## 7. 첫 구현 범위

첫 코딩 묶음은 다음까지만 진행한다.

1. `experiments/parser-v2` 실행기와 실행 manifest
2. 기존 입력 처리 재사용
3. 종횡비 `2.0` 기준 통짜/타일 분기
4. spark-1118 호출(선택 옵션은 서버 YAML 사용)
5. 좌표 복원·타일 중복 제거
6. OCR 줄 단일 귀속 및 미배정 보존
7. Label Studio에 `raw parsing / assigned / unassigned` 세 층 출력

이 단계에서는 Gemma를 호출하지 않는다. 결정론적인 앞부분이 맞는지 확인한 뒤 상품/패널
그룹핑부터 fc87 Gemma를 붙인다. 그래야 결과가 달라질 때 OCR·후처리·VLM 중 원인을 정확히
구분할 수 있다.
